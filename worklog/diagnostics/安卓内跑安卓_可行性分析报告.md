# 在安卓手机上跑安卓系统做软件测试 —— 可行性分析

**分析对象**：`/sdcard/DSH_ai/VM/AEmulator-Plus-main`（AEmulator Plus 工程）+ `RMX3888_14.0.0.228(CN01)` OTA 包
**被测宿主机**：RMX3888 / ColorOS 14 / Android 14 / SDK 34 / aarch64 / 8 核 / 11 GiB RAM
**分析方式**：不采信任何既有报告结论，全部关键项现场重测（命令与输出见附录 A）
**分析时间**：2026-11-15

---

## 0. 一句话结论

**在"这台手机、不 root、无 KVM、无 pVM"的条件下，把 Android 14 完整系统（ColorOS 14）跑起来做 App 测试，工程上做不到；把 AEmulator Plus 改造成能跑它的工程，投入产出比是负的。**

但需求本身（"在可控的 Android 环境里自动化测 App"）有两条真正走得通的路，见第 7 节。

判决依据只有三条硬事实，每一条都单独足以否掉这条路：

| # | 硬事实 | 证据强度 |
|---|---|---|
| H1 | 该 ROM 的内核**一个 virtio 块设备驱动都没有**（`CONFIG_VIRTIO_BLK=n`），放到 QEMU 上实测直接 `VFS: Cannot open root device` panic | 内核 config 实测 + 实机启动实测 |
| H2 | 宿主**没有 `/dev/kvm`、没有 `/dev/gunyah`**，且 vendor_boot 里写死 `androidboot.hypervisor.protected_vm.supported=0` | 现场探测 + bootconfig 解包 |
| H3 | 官方 Android Emulator **没有 linux-aarch64 主机分发**（只有 linux_x64 / darwin_x64 / darwin_aarch64 / windows_x64 / windows_aarch64），拿不到带 goldfish 设备模型的 QEMU | dl.google.com 仓库清单实测解析 |

H1 说明"用原 ROM 开机"这条路断了；H2 说明"用系统自带虚拟化框架"这条路断了；H3 说明"换一个设备模型完整的 QEMU fork"这条路也断了。

---

## 1. "可行性"到底按什么判

把模糊需求拆成三个独立判据，任一不满足即该方案不成立：

- **J1 能开机**：来宾系统能走到 `system_server` ready、能 `adb install`、能显示画面。
- **J2 能被测**：`adb`/`uiautomator`/`screencap`/`input` 能从 CI 侧驱动，能并发多实例。
- **J3 值得做**：启动时间、每实例成本、维护工时，比直接买/用真机便宜。

市面上很多"安卓里跑安卓"的讨论只盯 J1，实际决策死在 J3。

| 项目 | 实测值 | 命令/来源 |
|---|---|---|

| 存储 | 221 G，剩余 79 G | `df -h /sdcard` |
| `/dev/kvm` | **不存在** | `ls /dev/kvm` |

| 容器/沙箱能力 | `CapEff=0000…0`；`mount` 返回 0 但 `/proc/self/mountinfo` 无记录且不生效（影子挂载） | `mount -t tmpfs` + `grep mountinfo` |
| 用户命名空间 | `unshare -m` / `unshare -p --fork` 可执行 | 实测 |

**关于 AVF 的关键判断**：设备上确实装了完整 AVF 运行时（crosvm + microdroid），乍看"自带虚拟机"。但两道门都关着：

1. `protected_vm.supported=0` —— 厂商在 bootconfig 里显式关闭了 pVM，microdroid 起不来；
2. 即便开着，crosvm 只有 **KVM 后端**（crosvm 源码实测只出现 `kvm`，无 TCG 后端），而设备无 `/dev/kvm`。高通平台的 pVM 走的是 gunyah（`hvc_gunyah.ko` 在 vendor_dlkm 里），`/dev/gunyah` 这个节点在你当前可见命名空间里不存在。

### 3.2 站不住或严重误导的（必须修正）

| # | 报告怎么写 | 实测 | 影响 |
|---|---|---|---|
| E1 | 三处 `virtio` 命中 0 次 ⇒ "需换 GKI 内核" | 结论方向对，但**证据方法弱**（`strings` 计数只能证明字符串不在，不能证明功能不在）。**真正的铁证是内核 config**：`CONFIG_VIRTIO_BLK=n`、`VIRTIO_PCI=n`、`VIRTIO_MMIO=n`、`VIRTIO_NET=n`、`VIRTIO_CONSOLE=n`、`DRM_VIRTIO_GPU=n` | 报告结论侥幸正确，论证不合格 |
| E2 | inode 合计 20,261 | **20,420**（15 分区逐项相加，报告加法错 159） | 数据层小错，不影响决策 |
| E3 | 可删 3185.5 MB ⇒ 包体 8.24 → 6.14 GB | 算术自洽，但 §5.2 的"镜像节省"用的是**分区级压缩比推算**，§5.3 的 `9.41 GiB → 7.30 GiB` 无 `lpmake` 实测（报告 §9 自己承认未安装） | **伪优化**。见 E7 |
| E4 | `fsck.erofs --xattrs` 不还原 SELinux 上下文 | 表述含混：真实断点是 `mkfs.erofs` **重建时 xattr 丢失且未回填**（报告 §7 承认"未实现"） | 这恰恰是重打包路线真正会炸的地方 |
| E5 | §6.4「A. redroid 容器：mount namespace ✓」 | **判错**。`mount` 在本容器内返回 0 但挂载表无记录、对文件系统不生效；`/dev/loop*` 不存在，独立 EROFS 镜像挂不上 | 把 redroid 从"可行待确认"直接降为"不可行" |
| E6 | 「GKI 与该 ROM 同为 android14-11 KMI 代，vendor 模块按 GKI 契约兼容」 | **不成立**。①ROM 内核是 `-o-`（OEM 分支）不是 GKI；②`CONFIG_MODULE_SIG=y`，换内核后 387 个 vendor 模块签名与 vermagic 全部对不上；③vendor_boot vendor_ramdisk 里 387 个 `.ko` 全是**高通真机硬件**（`clk-qcom` `camcc-pineapple` `cnss2` `rmnet_*` `wcd939x_*`），在 virt 平台上探测即失败 | 「换内核就能开机」是错的：换内核 = 放弃这台设备的全部硬件适配，来宾不再是 ColorOS 14 |
| E7 | 「精简可省 2.15 GB，值得做」 | 对"手机内存里跑安卓"这件事，**2 GB 是伪瓶颈**。真瓶颈是 RAM（itely 11 GiB 总量里只剩 2.5–4 GiB）与 TCG 的 17–20× 慢，不是 2 GB 存储 | 精简工作的优先级应排到最末 |

### 3.3 报告完全没提、但决定成败的三条

- **N1**：vendor_boot 的 `first_stage_ramdisk/fstab.qcom` 要求 `avb_keys=…` + `logical`（动态分区）+ `slotselect`（A/B 槽）+ userdata 必须 `f2fs` 且 `fileencryption=aes-256-xts`。这意味着**即便内核换了，first-stage init 仍会因为没有 AVB 公钥链和 dm-linear 元数据而中止**。
- **N2**：`androidboot.hypervisor.protected_vm.supported=0` —— 设备自带虚拟化被厂商关死（见第 2 节）。
- **N3**：12 个 APEX + `apexd` 依赖可写 `/data` 并做 mount namespace 隔离；`/data` 要求 file-based encryption + metadata 分区。任何绕过真内核的方案都过不了这一关。

## 4. 工程现状：AEmulator Plus 到底是什么

审计结论（file:line 证据）：

| 维度 | 实况 | 证据 |
|---|---|---|
| 引擎 | **qemu-user（用户态翻译器）**，`qemu-arm 8.2.4`，只认 32 位 ARM | `libqemu_kk.so` 内字符串 `usage: qemu-arm …`、`linux-user/arm/cpu_loop.c`；全仓 `qemu-system` / `qemu-aarch64` 命中 **0** |
| 启动模型 | **App 自己当 init**，每个来宾服务单独 `exec` 一个 `qemu-arm` 进程 | `GuestVm.kt:24-26`；`GuestRunner.kt:8,45-46` → `qemu -L <root> -0 argv0` |
| 内核 | **从不引导来宾内核** | `docs/vm-archive.md:26-27`、`rom/cm11/device/.../BoardConfig.mk:4` `TARGET_NO_KERNEL := true` |
| mount | `mount()` 被桩成 `return 0`，`/proc/self/mounts` 是手写假表 | `native/guestshim/aemushim.c:25-30`、`TreeFixer.kt:1329-1342` |
| binder | **用户态守护进程**顶替内核驱动（`libbinderd_kk.so`） | `GuestVm.kt:686` |
| SELinux | 主动 patch 成 disabled | `TreeFixer.kt:149,945-952` |
| 文件系统 | ext4 / YAFFS2 / UBIFS / SquashFS / RFS / sparse / super / payload(受限) —— **EROFS 全仓 0 命中** | `Importer.kt:1324-1330`、`FirmwareToolset.java:1405-1421` |
| ADB | 宿主侧**自实现 ADB 线协议**，只 shell/exec/sync/reboot/root/remount，无 shell_v2/stat_v2 | `AdbServer.kt:22,176-191` |
| 自动化 | 无 uiautomator / appium / espresso / monkey；截图读裸 fb0 而非 `screencap` | 全仓 grep；`Screenshot.kt:21` |
| 包体 | assets 2.7 MB + jniLibs 8.5 MB | `du -sh` |
| `rom/cm11` | CM11 / **Android 4.4.2 / ARMv7** userdebug，426 project，`boot.img` 无内核 | `rom/cm11/README.md:14-16,73-74` |

**定性**：这是一个"**经典老固件用户态兼容层**"，不是虚拟机监视器。它把"厂商老系统"拆成一堆 32 位 ARM 进程在宿主内核上跑，用 shim 伪造内核接口。这套设计对 Android 2.x–7.x 很聪明，对 Android 14 完全不适用——A14 的 `init` 二阶段、`apexd`、`dm-verity`、`binder` 内核驱动、`fileencryption`、`f2fs` 都是**内核 ABI 级依赖**，用户态翻译器一个都提供不了。

## 5. 五条路径，逐条判决

| 路径 | 干什么 | J1 能开机 | J2 能被测 | J3 值得做 | 判决 |
|---|---|---|---|---|---|
| **P1** 原样把 AEmulator Plus 改造成跑 Android 14 | 沿用 qemu-user，补 64 位 + EROFS + APEX | ✗ | ✗ | ✗ | **架构级不可行** |
| **P2** qemu-system-aarch64 + TCG + **原 ROM** | 换引擎，保留 ColorOS | ✗（H1：内核无 virtio；N1：AVB/logical/f2fs 链断） | — | — | **不可行** |
| **P3** qemu-system-aarch64 + TCG + **GKI 内核 + 自建 system** | 弃厂商 ROM，换 AOSP/GSI | △ 理论可行 | △ | ✗（17–20× 慢） | **技术成立、决策不成立** |
| **P4** AVF / pVM（设备自带虚拟化） | 用 crosvm + microdroid | ✗（H2：`supported=0` + 无 KVM/Gunyah） | — | — | **不可行** |
| **P5** 容器化（redroid / 云手机本地方案） | 共享宿主内核跑 Android | ✗（无真 mount namespace、无 loop、无 binder_linux） | — | — | **本机不可行** |

### 5.1 P2 为什么一定失败（实测，不是推断）

我把 ROM 的 `boot.img` 内核单独拆出来，直接放到 `qemu-system-aarch64 -M virt` 上跑：

```
$ qemu-system-aarch64 -M virt,gic-version=3 -cpu cortex-a76 -smp 2 -m 2048 \
    -accel tcg,thread=multi -kernel rom_kernel.Image -append "console=ttyAMA0" -nographic
[    0.000000] Linux version 6.1.25-android14-11-o-g8dade92b4f59 …
[    0.000000] Machine model: linux,dummy-virt
[    1.259364] VFS: Cannot open root device "(null)" or unknown-block(0,0): error -6
[    1.266681] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)
```

挂上 virtio-blk 磁盘再试一次：

```
-append "… root=/dev/vda" -drive if=none,id=d0,file=testdisk.img -device virtio-blk-pci,drive=d0
[    1.113850] VFS: Cannot open root device "vda" or unknown-block(0,0): error -6
[    1.119541] Kernel panic - not syncing
```

dmesg 里 **`virtio` 出现 0 次，块设备一个都没枚举出来**。这是 H1 的直接实证。

### 5.2 P3 为什么技术成立但决策不成立

我用 Debian 官方 arm64 内核（`6.1.0-50-arm64`）+ 自制 initramfs 在同一套 QEMU/TCG 参数下**跑通了完整 aarch64 来宾**（能挂 virtio 盘、能起 busybox、能跑基准、能关机）：

```
$ qemu-system-aarch64 -M virt,gic-version=3 -cpu cortex-a76 -smp 2 -m 1024 \
    -accel tcg,thread=multi -kernel vmlinuz-6.1.0-50-arm64 -initrd initrd-bench.gz …
=== BENCH_START ===
GUEST_PRIMES=2262 WALL_MS=28250
GUEST_WRITE32_MS=850
GUEST_MD5_32MB_MS=510
=== BENCH_DONE ===
```

同一段 shell 素数筛（同一 busybox 二进制）在宿主上：

```
HOST=2262   real 1.400s
```

**三次来宾测量：24.32 s / 28.25 s / 28.67 s → 相对宿主慢 17.4×–20.5×。**

这个倍数外推到 Android 14 冷启动：真机 `boot_completed` 约 25–40 s，TCG 下约 **7–14 分钟**；而 `system_server` 的 `Watchdog`（默认 60 s）与 `ANR` 超时会密集误杀，导致**开机后服务反复重启**。J2 实测要求的并发多实例（每实例 ≥4 GiB + 4 vCPU）在 11 GiB / 8 核的机器上**最多 1 个**，且会把宿主系统拖死。

这就是 J3 死掉的点：单实例、十几分钟启动、跑一个 UI 测试用 3 分钟——不如买台千元机。

## 7. 结论与推荐路线

### 7.1 判死清单（这四条不要再投入）

1. 用原 ROM 在手机内启完整系统（P2）——H1 铁证。
2. 依赖设备自带虚拟化（P4）——`protected_vm.supported=0`。
3. 依赖容器跑 Android（P5）——无真 mount namespace / 无 loop。
4. 继续按现有 qemu-user 架构往 Android 14 改（P1）——差的是内核态，不是补几个 shim。

### 7.2 推荐路线

#### 路线 A（主选，立刻可做）：不追"跑在手机里"，改成"真机 + ADB 网格"

把需求从"跑安卓系统"翻译成"跑够用的安卓设备"：

- 本机自带的 Android 14 就是最真实的测试目标；再加 2–3 台二手真机（覆盖 Android 10/12/14 三档）。
- 每台挂 `adb over TCP`，CI 侧用 `uiautomator2` / `Appium` 驱动，`scrcpy` 做投屏回看。
- 并发用端口矩阵（5555/5557/5559…），单机能耗/发热可控。
- **AEmulator Plus 保留做它真正擅长的事**：Android 2.2–7.x 老版本兼容回归。这部分工程已经完整，无需改造。

交付物（可直接照做）：

```bash
# 每台设备
adb -s <serial> tcpip 5555
adb connect <phone-ip>:5555
adb -s <phone-ip>:5555 install -r app-under-test.apk
adb -s <phone-ip>:5555 shell uiautomator dump /sdcard/ui.xml
adb -s <phone-ip>:5555 shell screencap -p /sdcard/s.png
adb -s <phone-ip>:5555 pull /sdcard/{ui.xml,s.png} .
```

CI 侧（uiautomator2）：

```python
import uiautomator2 as u2
devices = [u2.connect(f"{ip}:{5555+i}") for i, ip in enumerate(IPS)]
for d in devices:
    d.app_install("app-under-test.apk")
    d(text="登录").click()
```

**验收判据**：3 台设备同时跑同一套用例，通过率 100%，单轮 < 3 分钟，`adb devices` 稳定不掉线 24 h。

#### 路线 B（备选，想保留"手机内跑"的方向）：qemu-system TCG + 自建 AOSP 14 精简系统

目标**不是跑 ColorOS**，而是"跑一个能装你 APK 的 Android 14"。技术链我已实测跑通 arm64 来宾，缺的是 Android 侧的设备模型与 HAL。

关键取舍：
- 内核用 **GKI `android14-6.1`**（不是 OEM 的 `-o-` 内核），开 `VIRTIO_BLK/PCI/MMIO/NET/GPU`；
- system 用 **AOSP 14 `aosp_arm64` / `sdk_phone64_arm64`** 构建，不用厂商 ROM；
- 图形走 **virtio-gpu + SwiftShader**（软件光栅化），J2 的 `screencap` 在软件渲染下可用；
- `adb` 用 QEMU user-net `hostfwd=tcp::5555-:5555` 转发到来宾 `adbd`。

实测得出的一条硬限制：**上游 QEMU 8.2 缺 Android 模拟器设备模型**。既有实验记录（`/root/vmwork/and-fail-summary.txt`）显示，官方 `google_apis 34_r06` 系统镜像在 upstream QEMU 上：

- 5 个 virtio 盘全部正确枚举（`vda`…`vde`，GPT 正确，`vdc=/data` 符合 fstab）；
- 卡在 first-stage mount，**2.7 s 时静默 `reboot bootloader`**，无第二阶段日志；
- 已排除盘序/内容、fstab、CPU 型号、TCG 线程、PCI vs MMIO。

结论：**必须补 goldfish pipe / qemud property 通道**，或者改用 Cuttlefish 的 device tree + 自建 kernel cmdline。这条工程量级 = XL（自建 Android 14 来宾镜像 + 补 QEMU 设备模型 + 自建 HAL）。

**验收判据（M 阶段）**：
- M1：`qemu-system-aarch64` 在手机内 TCG 启动 arm64 Linux 来宾 → **已达成**（本次实测）；

**我的判断**：M2 之前投入都还是"研究"，M3 达成后单实例 J3 仍然输给路线 A。所以 M1 之后应当**先试路线 A，再用路线 B 做补充**（比如需要 root/多版本并发的场景）。

## R1-2 root 改变了什么，没改变什么

**root 解决了的（从 X2 的"不可行"升级）**：

- `mount` / `losetup` / `chroot` / `unshare` / `nsenter` 在真机 root 侧可用，容器侧那个"mount 返回 0 但不生效、无 loop"的限制**是 DSH 容器的沙箱视图，不是真机**。
- `binderfs`（`binder` / `hwbinder` / `vndbinder`）、`ashmem`、`overlayfs`、`veth`、`tun`、`nf_conntrack`、`EROFS+LZ4` 全在内核里。
- 于是 **P5 容器/chroot 路线**从"本机不可行"改成 **"有条件可行"**。

**root 解决不了的（这才是关键）**：

| 阻塞 | 为什么 root 也变不出来 |
|---|---|
| `/dev/kvm` | 硬件/固件层。`CONFIG_KVM=y` 只是编进内核，但 cmdline `kvm-arm.mode=protected` 且 **MTK GenieZone 已占 EL2**（`/dev/gz_ffa_dev` 在），KVM 不以 `/dev/kvm` 暴露给 userspace。root 改不了 EL2 归属 |
| AVF / pVM | `vm info` 官方判决 `VMs are not supported`，三个 feature 全 disabled，`virtualizationservice` 没起。这是 vendor 配置 + hypervisor 缺失，root 起个服务也没用 |
| **PID_NS / USER_NS** | **`CONFIG_PID_NS is not set`、`CONFIG_USER_NS is not set`** —— 内核没编，root 也 `modprobe` 不出来（不是模块，是编译期开关）。完整 Android init 需要独立 PID 1 与 pid namespace；缺失即无法给来宾一套独立进程树 |
| 宿主 virtio 设备驱动 | `VIRTIO_BLK/NET/PCI/MMIO/GPU` 全关。注意：有的那几个（`VIRTIO_FS`/`VHOST_VSOCK`/`BLK_MQ_VIRTIO`）是**给 guest 当后端**用的，不是**当 guest 用块设备**用的 |
| ROM 内核零 virtio | H1 不变，与 root 无关 |
| 官方 Emulator 无 linux-aarch64 版 | H3 不变，与 root 无关 |
| TCG 17–20× 慢 | 与 root 无关；root 只是让 `qemu-system-aarch64` 能跑起来（Termux 有 `qemu-system-aarch64-headless 11.1.3`），不改变性能包络 |

| **P1** qemu-user 改造跑 A14 | 架构不可行 | **不变** | 差的是内核态，与 root 无关 |
| **P2** 原 ROM + qemu-system TCG | 不可行（H1） | **不变** | ROM 内核 `VIRTIO_BLK=n`，实测 panic；与 root 无关 |
| **P3** GKI + 自建 AOSP + TCG | 技术成立 / J3 不成立 | **升级：从"容器内跑不了"变成"真机 root 下能跑"**，但 **J3 仍不成立** | root 解除 `CapEff=0` 限制，Termux 可直接装 qemu-system-aarch64；但 17–20× 慢、7–14 min 冷启动、11 GiB 只够 1 实例，结论不变 |
| **P4** AVF / pVM | 不可行（H2） | **更死了** | 新增官方 `vm info` 权威判决 + GenieZone 占 EL2 + 三 feature 全 disabled，不是"配置没开"而是"vendor 不支持" |
| **P5** 容器 / redroid | 本机不可行 | **改判：有条件可行，未验证** | root + loop + mount + binderfs + overlay + netns/utsns/mntns + EROFS 全具备；**但 PID_NS/USER_NS 编译期缺失 + SELinux Enforcing + 共享宿主内核**。按老大只读要求，**没有实测 `mount`/`chroot`** |
| **P6（新增，主选）** 直接把这台 root 真机当测试台 | — | **判为最优先** | 见下 |

### P5 "有条件可行"的准确含义（别误读）

即便 root 全开，容器路线能给的也**不是"独立 Android 14 完整系统"**，而是：

- 共享宿主 `6.1.115` 内核（因为不能引导内核，`/dev/kvm` 也没有）；
- 来宾是**同一内核上的第二套 Android 用户态实例**，PID 空间与宿主共用（PID_NS 缺失）；
- 因此跑出来的还是 **Android 15 / realme UI 的用户态**，不是 ROM 包里的 ColorOS 14；
- 想要"ColorOS 14 / SDK 34"这个被测系统，容器路线给不了。

它真正能用的场景是：**在同一台机器上多开一个隔离的 App 运行环境**（多账号、并行测试、脏环境快照回滚），不是"复刻另一个 ROM"。

### P6 为什么是主选

老大要的是"**在安卓上跑安卓进行软件测试**"。按 R1-1 的实测，这台机器**现在就已经是那个东西，而且比虚拟出来的更好**：

- Android **15** / SDK 35（比 ROM 里的 14 还新，覆盖更值钱）；
- 真 root（KernelSU）+ Zygisk + LSPosed + `tricky_store` + `hma_oss_zygisk` → 能 Hook、能改环境、能过检测、能注入；
- 8 核 / 11.1 GiB / 14 GiB zram / 71 G 空闲；
- 装 APK、`uiautomator dump`、`screencap`、`input`、`am`、`pm`、`logcat` 全部原生可用，**零启动开销**；
- 要测多版本覆盖，补 1–2 台二手真机挂 ADB 网格即可（路线 A 不变）。

对比：P3 花 XL 工程量换一个 17–20× 慢、7–14 分钟启动、单实例的 Android 14；P5 花 L 工程量换一个共内核、共 PID 空间的"第二实例"。**两者都不如直接用这台机器**。

## R1-4 只读承诺下"没做"的验证，与放行后的命令清单

**本轮明确没有做**（避免误判为已验证）：`mount --bind` / `mount -t erofs` / `losetup` 关联镜像 / `chroot` / `unshare -m` 后建真挂载 / `setprop service.adb.tcp.port 5555` / `start adbd` / 启动 `virtualizationservice` / 编译或加载内核模块 / 写任何设备分区。

若老大放行写操作，**按此顺序验证，每步先定成功判据**：

```bash
# V1 真机 root 下 mount 是否真生效（验证 X2 是否确实解除）
mkdir -p /data/local/tmp/_vmtest/{src,dst} && touch /data/local/tmp/_vmtest/src/marker
mount --bind /data/local/tmp/_vmtest/src /data/local/tmp/_vmtest/dst
grep _vmtest /proc/self/mountinfo          # 判据：有记录（容器侧为 0 条）
ls /data/local/tmp/_vmtest/dst             # 判据：能看到 marker

# V2 EROFS 镜像能否挂载（用 ROM 里已提取的 system.img）
losetup -f --show /sdcard/DSH_ai/VM/_verify/images2/system.img   # 判据：返回 /dev/block/loopN
mount -t erofs -o ro /dev/block/loopN /data/local/tmp/_vmtest/erofs
ls /data/local/tmp/_vmtest/erofs/build.prop                        # 判据：能读

# V3 PID/USER namespace 缺失是否致命（预期失败，属确认性验证）
unshare -p --fork true                     # 判据：EINVAL/ENOSYS → 坐实 R1-2
unshare -U true                           # 判据：失败 → USER_NS 编译期关闭

# V4 拉起 adbd（老大说已授予 adb，但实测 adbd=stopped）
setprop service.adb.tcp.port 5555
setprop persist.adb.tls_server.enable 1    # 无线调试
# 或 setprop sys.usb.config adb             # USB 调试
getprop init.svc.adbd                      # 判据：running
adb connect 127.0.0.1:5555 && adb shell id

# V5 真机侧 TCG 复测（验证 root 解除沙箱后的真实性能）
pkg install qemu-system-aarch64-headless  # Termux；或复用已下载的二进制
qemu-system-aarch64 -M virt,gic-version=3 -cpu max -smp 4 -m 2048 \
  -accel tcg,thread=multi -kernel <gki-Image> -initrd <initrd> \
  -append "console=ttyAMA0 rdinit=/init" -nographic
# 判据：重跑素数筛，对比宿主 1.4 s，看是否仍 17–20×
```

**V1/V2 通过**才值得往 P5 走；**V3 失败**（预计必然）就把 P5 锁死在"共 PID 空间的第二实例"这个上限内。

## R1-5 修订后的最终结论

1. **X1/X2 两个前提错误已纠正**：宿主是 `RMX5062`/MTK/Android 15，不是 ROM 的 `RMX3888`/高通/Android 14；容器沙箱限制不等于真机 root 限制。
2. **root 把 P5 从"不可行"抬到"有条件可行、未验证"，把 P3 从"跑不起来"抬到"跑得起来但依然不值"**；**P1/P2/P4 全部原判不变**，其中 P4 因 `vm info` 官方判决而更确定。
3. **`CONFIG_PID_NS`/`CONFIG_USER_NS` 编译期缺失 + GenieZone 占 EL2 + `/dev/kvm` 不存在**，是 root 也翻不过去的三道硬墙。这三道墙决定了"完整独立 Android 系统"在这台机器上没有原生虚拟化路径。
4. **对"软件测试"这个真实目标，最优先是把这台已 root、已装 LSPosed 的 Android 15 真机直接当测试台（P6）**，需要多版本覆盖就补真机 ADB 网格（原路线 A）。AEmulator Plus 保留做它擅长的 Android 2.x–7.x 老版本回归，P0-1/2/3 三个接口补齐的优先级不变。
5. **ROM 包本身仍是最有价值的"离线素材"**：它的 EROFS 分区、375 个 APK、依赖引用、SELinux 上下文，是做静态分析/兼容性基线/差分包研究的现成数据；只是不该被用来"开机"。
