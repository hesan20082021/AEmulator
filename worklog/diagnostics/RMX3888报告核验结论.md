## 1. 硬错误（6 处，逐条附实测证据）

### E1 ❌ 「容器根文件系统 /dev/block/dm-71」错误

| | 报告 §6.1 | 实测 |
|---|---|---|
| 声明 | `/dev/block/dm-71`，221 G | `/dev/block/dm-18`，**erofs**，221 G |
| 实证 | — | `findmnt -T /` → `TARGET=/ SOURCE=/dev/block/dm-18 FSTYPE=erofs` |

**dm-71 是 `/data`（f2fs），不是容器根。** 报告把 /data 的设备号写成了根。

### E2 ❌ 「/tmp 文件系统 tmpfs（内存盘）」— 与 `stat -f` 冲突

`stat -f -c %T /tmp` → **f2fs**；但 `findmnt -T /tmp` / `df -T /tmp` → **tmpfs**；`/proc/self/mountinfo` → `tmpfs on /tmp tmpfs rw,seclabel,size=5777092k`。

实测结论：`/tmp` **确实是 tmpfs**（报告对），但 `stat -f` 会返回 f2fs（因为该容器对 tmpfs 做了 overlay/fuse 视图）。报告在别处用 `stat -f` 取容器根 fs 时同样会被这个偏差带偏 —— **这正是 E1 的成因**。

### E3 ❌ §5.3 「组内实际占用 9.41 GiB → 7.30 GiB」无来源

报告 §5.3 给出精确到 GiB 的两个数，但：
- §5.2 明说镜像是"按各分区实测压缩比**推算**"
- 组内占用应由 `lpmake`/super 元数据读出，报告 §9.3 承认「lpmake 未安装未验证」
- ⇒ 9.41 / 7.30 / +2.10 三个数是**推算值冒充实测值**，来源等级被错标为 A

### E4 ❌ §3.2 inode 合计 20,261 与实测 20,420 不符

用 `lists/sidecar_*.json` 逐分区 `count` 求和：

```
system 3563 + system_ext 3485 + product 251 + vendor 3659 + odm 2615
+ my_product 1256 + my_stock 2201 + my_bigball 672 + my_heytap 326
+ my_region 1873 + my_carrier 12 + my_manifest 22 + my_engineering 21
+ vendor_dlkm 348 + system_dlkm 116
= 20420
```

报告写 **20,261**，差 **159**。逐分区数值全部正确（15/15 命中），**合计是加法错误**。

### E5 ❌ §4.5「对 A+B 组的 68 个包做全树 XML 检索，命中 33 个包」

实测 `lists/candidates.json`：A+B 组 = **70 个包**（不是 68）。
实测 `lists/dep_check_results.json`：**70 个 key，64 个有非空引用**，引用实例 **488 条**。

报告说"68 个包检索、命中 33 个"——**检索数与命中数双错**。且 §4.5 的"逐项引用明细"表里 `com.redteamobile.roaming` 单独就标了 12 处引用，说明"33 个包"这个数不可能是实例数。

### E6 ❌ §3.3「fsck.erofs --xattrs 不还原 SELinux 上下文（所有文件被赋同一上下文）」表述不准

实测：erofs-utils 1.8.5 的 `fsck.erofs --extract` 确实**不**写回 xattr；但报告接着说"容器内 setxattr security.selinux 写入成功"，两者混在一起陈述，读者会误以为 fsck 会保留。真正的问题是 `mkfs.erofs` 重建时 xattr 丢失，而报告 §7 承认"元数据回填 —— **未实现**"。**表述应改为：xattr 在重建链路中丢失且未回填，这才是会破坏 SELinux 的真实断点。**

## 2. 重要遗漏（3 处，均改变结论）

### O1 🚫 漏报：**宿主真机本身就是 RMX3888，且带完整 OPlus 动态分区布局**

`/proc/self/mounts` 实测（容器内可见宿主挂载表）：

```
/my_product      erofs   /dev/block/dm-23
/my_engineering  erofs   /dev/block/dm-24
/my_carrier      erofs   /dev/block/dm-26
/my_region       erofs   /dev/block/dm-27
/my_heytap       erofs   /dev/block/dm-28
/my_stock        erofs   /dev/block/dm-29
/my_bigball      erofs   /dev/block/dm-31
/my_manifest     erofs   /dev/block/dm-32
/product/app     overlay (lowerdir=my_region:my_preload:my_product:my_heytap:my_stock:my_engineering:product)
```

**这台宿主的分区结构与被分析的 ROM 完全同构。** 报告 §8 写"未触碰宿主真机 /system"，但整个 §2 的"48 分区 / 15 动态分区"结构，宿主上原样就有一套。

⇒ **这直接改变 redroid 路径的评估**：报告 §6.4 说 redroid 需要"erofs 可挂载"并标注"需宿主内核加载模块确认"。实测**宿主内核 erofs 是 builtin 且正在使用**（`/` 本身就是 erofs），该前提**已满足**，不必再"确认"。红android 路径的真正阻塞点不是 erofs，而是 §6.1 那条更硬的事实（见 O2）。

### O2 🚫 漏报：**容器内 mount syscall 返回 0 但不生效** —— 直接推翻 redroid 路径可行性

这是本次核验最重要的发现，报告完全没提。

实测（`/root/mtest`，独立目录，排除嵌套干扰）：

```
mount --bind /root/mtest/s1 /root/mtest/d1   → rc=0, errno=0
写 /root/mtest/d1/w.txt 后，/root/mtest/s1 内容 = ['mark.txt', 'w.txt']
   ↑ 文件"穿透"了，说明 bind 生效了

mount -t tmpfs none /root/mtest/d2           → rc=0, errno=0
/root/mtest/d2 内容 = []   ← 预置的 pre.txt 被隐藏，tmpfs 生效了

但：/proc/self/mountinfo 中 grep "mtest" → 无任何记录
    /proc/self/mounts   中 grep "mtest" → 无任何记录
```

**结论：mount 在本容器内是"影子挂载"——syscall 返回成功、语义上部分生效（bind 穿透、tmpfs 遮蔽），但不进入挂载表，因此不隔离、不持久、对容器外不可见。**

更进一步，`unshare -m` 也一样：

```
unshare -m --propagation private sh -c 'mount -t tmpfs t /mnt && echo NS_MOUNT_OK'
→ NS_MOUNT_OK          （命令成功）
但 /proc/self/mountinfo 里找不到该挂载
```

⇒ **redroid 路线的前提被推翻**：redroid 依赖 `mount namespace + binder + erofs` 三件套，其中 mount namespace 在本环境**不能建立真正的隔离挂载**，容器内看到的挂载表与内核实际状态脱节。报告 §6.4 给出的 "A. redroid 容器 → mount namespace ✓" 这条 ✔ **是错的**。

### O3 ⚠️ 漏报：**本机 /dev/loop* 不存在，`losetup -f` 权限拒绝**

```
ls /dev/loop*           → No such file or directory
losetup -f              → cannot find an unused loop device: Permission denied
mount -t erofs system.img /root/erofs_mnt → mount failed: No such file or directory (rc=32)
```

报告 §6.4 把「erofs 可挂载」列为 redroid 前提，但实测**本容器无法挂载任何独立 EROFS 镜像**（宿主 / 是 erofs 只是说明内核支持，不代表容器内能新挂）。

⇒ 更正后的表述应是：**内核 erofs 支持存在（builtin），但容器内无 loop 设备、无真实挂载能力**，这两个事实必须分开写。

## 6. 一句话结论

> 报告的**数据层**（分区表、inode、virtio 命中、AVB、模块数、体积核算）经独立复现**基本全部成立，质量高**；
> 但**环境判定层**（容器根设备、/tmp 类型、inode 合计、依赖命中数、redroid 前提）有 6 处实测冲突，
> 且**漏报了本机最关键的三条事实**——宿主本身就是同型 RMX3888、mount 是影子挂载、容器内无 loop 设备。
> 其中「mount 影子挂载」一条足以把 redroid 路线从"可行待确认"降级为"本机不可行"。
